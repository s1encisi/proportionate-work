# Paper and Documentation Writing Rules (Read as Needed)

Documentation language: English. See the [Chinese version](writing.md).

Applies to README files, project introductions, papers, reports, abstracts, conclusions, presentation materials, and similar writing tasks.

## 1. Write for the document's purpose

- README helps readers understand and use the project.
- A project introduction explains functionality and value.
- A paper explains research questions, methods, evidence, and contributions.
- An audit report identifies and describes substantive problems.

Do not turn every document into a risk assessment.

## 2. Handle four types of information appropriately

1. Confirmed problems that affect current use or conclusions: state them accurately, with detail proportionate to their importance.
2. Research boundaries necessary to define what a conclusion means: state them accurately, with appropriate detail.
3. Unstudied areas that do not affect the current claim: discuss them only when readers need them, the user requests them, or the document's conventions require them.
4. Purely imagined defects without supporting evidence: omit them from the text.

## 3. Factual boundaries do not require repeated disclaimers

- For research using data from one factory, describe the data source and research object to establish scope naturally.
- Do not repeatedly add "not demonstrated to work for every factory" to the abstract, every results section, the conclusion, and the project introduction.
- If a boundary determines whether a particular conclusion holds, retain the necessary qualification beside that conclusion. Do not move it elsewhere in a way that misleads readers.

## 4. State supported findings directly

- Use clear language whose strength matches the evidence.
- Do not mechanically insert vague phrases such as "for reference only," "not yet mature," "cannot be guaranteed," or "may have some potential."
- Do not invent effects, expand the scope of applicability, or describe association as causation when the evidence does not establish those claims.

## 5. Place limitations appropriately

- Explain each substantive limitation once in a suitable place, unless independently read sections or applicable requirements genuinely call for repetition.
- Do not automatically add limitations, risks, threat model, or known issues sections unless requested.
- Complete explicitly requested peer review, diagnosis, limitations analysis, or risk audits thoroughly. This skill is not a reason to avoid criticism.

## 6. Revise toward a concrete objective

- Revise content, logic, wording, or formatting according to the user's request.
- Stop when the objective is met. Do not repeatedly rewrite an entire document in pursuit of undefined standards of greater rigor or perfection.
- Do not unilaterally delete valuable and accurate limitations already in the text or exaggerate their severity.
